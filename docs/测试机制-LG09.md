## 3. 上线前测试流程

顺序：冒烟 → 功能 → 接口 → 回归 → 清单确认。上一层未通过不得进入下一层（书面接受风险除外）。

| 类型 | 要求 |
|------|------|
| 冒烟 | 同第 2.2 节；发版前再跑一次 |
| 功能 | 按变更验证：登录/配置、模型广场或定价、渠道转发、计费额度（测试账号） |
| 接口 | 见下表 R1～R8 |
| 回归 | 回归脚本全过；触及转发/计费时加测 Token 调用 |

**接口门禁**

| 编号 | 请求 | 通过条件 |
|------|------|----------|
| R1 | GET /api/status | success = true |
| R2 | GET /api/pricing | HTTP 200 |
| R3 | GET /api/notice | HTTP 200 |
| R4 | GET /api/about | HTTP 200 |
| R5 | GET / | HTTP 200 |
| R6 | GET /pricing | HTTP 200 |
| R7 | GET /v1/models（无 Token） | 非 5xx |
| R8 | 登录后控制台 / 模型广场 | 可进入且有数据 |

有 Token 时建议：`GET /v1/models` + Bearer → 200。

**检查清单（摘要）**

| 阶段 | 勾选项 |
|------|--------|
| 发布前 | 通知；Tag/合并；冒烟+接口+回归通过；按需压测；库可回滚；配置未串环境；评审/审批通过 |

## 4. 压力测试方案

**对象：** 网关只读 / 入口接口。默认不压聊天、生图、视频、计费接口。

**何时做：** 大版本、依赖/DB/网关变更、预期流量上升、近期有超时或 5xx、上线前评估有性能风险。小修复可不压，但须完成第 3 章。

**约束：** 仅测试环境；群内知会；低峰；单次 3～10 分钟。

| 编号 | 场景 | 接口 | 并发 | 时长 | 通过标准 |
|------|------|------|------|------|----------|
| S1 | 存活 | GET /api/status | 20～50 | 3 min | 错误率 < 1%；同机房 P95 < 500ms；公网 P95 < 2s |
| S2 | 定价 | GET /api/pricing | 10～30 | 3 min | 错误率 < 1%；同机房 P95 < 1s |
| S3 | 入口 | GET / | ~20 | 3 min | HTTP 200；错误率 < 1% |

关注：错误率、P95、CPU、DB 连接/慢查询。排查：应用/Nginx → PG → Redis → 限流或扩容。

```bash
BASE=https://modelrec.net
hey -n 3000 -c 30 "$BASE/api/status"
hey -n 1500 -c 20 "$BASE/api/pricing"
```

```powershell
powershell -ExecutionPolicy Bypass -File scripts/test/load-smoke.ps1 -BaseUrl https://modelrec.net
```

记录：日期、操作人、场景、参数、成功/失败、错误率、P95、结论。

## 5. 质量保障机制

本章与第 6 章「后台发布流程」分开：发布管怎么上线，本章管长期质量能力怎么建。  
下列能力**当前多数尚未落地，作为后续建设方向**；建设完成后可再回写本章并提高门禁要求。

### 5.1 代码覆盖率与静态扫描（待建设）

| 项 | 目标 |
|----|------|
| 单元测试覆盖率 | 对核心包（计费、转发、鉴权等）设定覆盖率门槛，合入前产出报告 |
| 静态扫描 | 引入 go vet / golangci-lint 等，阻断高危问题合入 |

现状：以开发自测及按需 `go test` 为主，无强制覆盖率门槛，无流水线静态扫描。

### 5.2 自动化测试策略（待建设；部分已有脚本）

| 项 | 说明 |
|----|------|
| 目标 | 接口自动化：核心网关/管理接口回归进 CI，PR 或合并后自动执行 |
| 范围建议 | 鉴权、定价、转发、计费相关路径逐步覆盖 |
| 已有基础 | 本地/发版前可跑：`scripts/test/api-regression.*`、`load-smoke.ps1`（尚未接入 CI） |

### 5.3 监控告警（待建设）

| 维度 | 目标 |
|------|------|
| 日志 | 错误日志聚合；关键错误关键字告警 |
| 指标 | QPS、延迟、5xx 率、进程存活 |
| 链路 | 关键转发路径可追踪（按需） |

现状：以机器日志 + 人工巡检为主；发布后短时健康检查见第 6 章。完整监控告警后续建设。

### 5.4 日常质量度量（待建设）

| 度量 | 说明 |
|------|------|
| 缺陷密度 | 版本缺陷数 / 变更规模（故事点或 MR 数） |
| 漏测率 | 上线后暴露、且本应在测试阶段发现的缺陷占比 |
| 回归通过率 | 发版前自动化回归通过情况（自动化落地后统计） |

现状：缺陷按 P0～P3 约定处理（见下），尚未做定期度量看板。

**缺陷分级约定（现行，支撑后续度量）**

| 级别 | 含义 | 要求 |
|------|------|------|
| P0 | 不可用 / 无法登录 / 大面积 5xx / 错计费 | 立即停发或回滚 |
| P1 | 核心转发失败、重要页无数据 | 上线前必须修复或书面延期 |
| P2 | 次要功能问题 | 可排期，发版说明 |
| P3 | 文案等 | 记录后迭代 |

未关闭 P0/P1 不得上线。

## 7. 回滚预案

**触发：** status 连续失败；无法登录或大面积 5xx；核心转发/计费异常；审批认定必须撤回。

**原则：** 先恢复服务；回到上一成功二进制；回滚后重跑冒烟与接口门禁；群内同步并留痕。

**步骤（/www/wwwroot/new-api）**

1. 宣布回滚，停掉当前 `new-api`  
2. 用发布前备份恢复（如 `new-api.bak.YYYYMMDD`）并赋权  
3. 启动，确认进程与端口  
4. 跑回归脚本，确认 status 与关键页面  
5. 同步结果，登记原因与后续计划  

发布前必须备份；未备份不得继续发布。  
二进制按上回退；误改 `.env` 才回退配置；破坏性 DB 变更须另有库备份预案。

**回滚后确认：** status、首页/登录、模型广场/定价、回归通过、缺陷已记录。
