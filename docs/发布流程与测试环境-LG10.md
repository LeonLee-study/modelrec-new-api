## 2. 测试环境：环境配置

### 2.1 必备组件

1. **MySQL 8**（本仓库本地联调当前用法）
2. **Go 1.22+**（本机开发跑后端）
3. （可选）**Redis** — 不配也能起，多节点 / 缓存场景再开
4. （可选）Docker — 用于接近线上的整包部署

### 2.2 环境变量（`.env`）

从示例复制后按环境改：

```sh
cp .env.example .env
```

测试 / 本机联调最小配置示例（密码按实际修改，勿提交真实密钥到 Git）：

```env
PORT=3000
TZ=Asia/Shanghai
SQL_DSN=root:你的密码@tcp(127.0.0.1:3306)/new-api?charset=utf8mb4&parseTime=True&loc=Local
SESSION_SECRET=请改成随机长字符串
GENERATE_DEFAULT_TOKEN=true
GIN_MODE=release
```

说明：

- `SQL_DSN`：指向测试库；库名建议固定为 `new-api`
- `SESSION_SECRET`：多机或长期测试环境必须改掉默认值
- 生产用独立 `.env` / 服务器环境变量，**不要**和本机共用同一套密码文档外传

### 2.3 数据库初始化

MySQL 中建库（只需一次）：

```sql
CREATE DATABASE IF NOT EXISTS `new-api`
  DEFAULT CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;
```

表结构由服务首次启动时 GORM AutoMigrate 创建，无需手写全量 DDL。

检查连通：

```sh
# Windows 示例（按本机 mysql 客户端路径调整）
mysql -uroot -p --host=127.0.0.1 --port=3306 -e "SHOW DATABASES LIKE 'new-api';"
```

## 3. 测试环境：服务启动

### 3.1 方式 A — 本机开发（当前团队 Windows 联调）

1. **先启动 MySQL**  
   - 若为本机解压版：执行 `C:\Users\PC\MySQL\start-mysql.bat`（或等价启动脚本）  
   - 确认 `127.0.0.1:3306` 在监听  
2. 确认项目根目录 `.env` 已配置且能连上 `new-api` 库  
3. 启动后端：

```sh
go run main.go --log-dir ./logs
```

4. 浏览器访问：`http://localhost:3000/`  
5. 健康检查：`http://localhost:3000/api/status`（应返回 success）

前端热更新（可选）：

```sh
cd web/default
bun install
bun run dev
```

### 3.2 方式 B — Docker Compose（接近部署形态）

仓库已有：

- `docker-compose.yml`：全容器（默认 PostgreSQL + Redis）
- `docker-compose.dev.yml`：开发向
- `docker-compose-local.yml`：宿主机网络访问本机库

启动示例：

```sh
docker compose -f docker-compose.yml up -d
docker logs -f new-api
```

若测试机坚持用 MySQL：在对应 compose 里改用注释中的 MySQL `SQL_DSN`，并启用 `mysql` 服务（见 `docker-compose.yml` 注释段）。

### 3.3 启动检查清单（后端自测）

- [ ] MySQL 进程 / 服务已启动，3306 可连  
- [ ] `new-api` 库存在  
- [ ] `.env` 中 `SQL_DSN` 正确  
- [ ] `go run` 或容器无报 DB 连接错误  
- [ ] `/api/status` 正常  
- [ ] 能打开管理后台并登录（首次按项目向导）

## 4. 发版流程（服务侧）

### 4.1 现有自动化（GitHub Actions）

| 触发 | Workflow | 产物 |
|------|----------|------|
| 推送 tag（非 alpha/nightly 等规则见文件） | `release.yml` | 多平台二进制 + GitHub Release |
| 推送 tag | `docker-build.yml` | Docker 镜像推送 |
| 推 `alpha` 分支 | `docker-image-alpha.yml` | alpha 镜像 |
| 推 `nightly` 分支 | `docker-image-nightly.yml` | nightly 镜像 |
| 开 PR | `pr-check.yml` | **仅** PR 模板 / 质量门禁，**不**跑编译测试 |

查看红绿：仓库 GitHub → **Actions**。

### 4.2 建议发版步骤（测试 → 预发 / 生产）

1. **代码合并**到约定分支（由 amy 定主干策略）  
2. **打 tag**（示例：`vX.Y.Z` 或团队约定的测试 tag）并 push  
3. 在 Actions 确认 `Release` / `Publish Docker image` **绿色**  
4. **测试机更新**（二选一或按环境定）：  
   - Docker：`docker pull <镜像>:<tag>` → 改 compose / 重启容器  
   - 二进制：从 Release 下载对应平台包 → 停旧进程 → 替换 → 带同一套 `.env` 启动  
5. **冒烟**：`/api/status`、登录、一条核心业务接口  
6. 回写发版记录（tag、时间、操作人、是否回滚）

### 4.3 回滚（服务侧）

1. 重新拉上一个已知可用的镜像 tag / 二进制  
2. 重启服务（库一般向前兼容；若有破坏性迁移需单独预案）  
3. 再跑一遍冒烟清单  

### 4.4 发版服务侧检查清单

- [ ] tag / 分支符合约定  
- [ ] Actions 构建成功  
- [ ] 测试机 `.env` / 密钥未误用生产  
- [ ] 数据库已备份（正式发版前）  
- [ ] 服务起来且健康检查通过  
- [ ] 通知前端 / 联调同学新环境地址与版本号

## 6. 本机联调备注（Windows）

当前常见坑：`2002 / 10061` = MySQL 没启动，先跑启动脚本再连 Navicat / 再起后端。  
Navicat 能连库 **不等于** 后端已启动；跑接口前还要 `go run` 或起容器。

本机一键起库：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/windows/start-test-env.ps1
```

然后：

```powershell
$env:GOPROXY='https://goproxy.cn,direct'
go run main.go --log-dir ./logs
```

### 7.2 服务侧日常操作（这台机）

查看进程：

```sh
ps aux | grep '[.]/new-api'
```

重启（在运行目录）：

```sh
cd /www/wwwroot/new-api
# 先停旧进程（按实际 PID），再启动：
nohup ./new-api --log-dir ./logs > ./logs/nohup.out 2>&1 &
curl -s http://127.0.0.1:3000/api/status
```

发版更新建议流程：

1. 在本机构建或从 Release / CI 取 Linux 二进制  
2. 备份：`cp /www/wwwroot/new-api/new-api /www/wwwroot/new-api/new-api.bak.$(date +%F)`  
3. 上传覆盖 `/www/wwwroot/new-api/new-api`，`chmod +x`  
4. 重启进程，打 `/api/status` 与登录冒烟  
5. 异常则回滚 bak 再重启
